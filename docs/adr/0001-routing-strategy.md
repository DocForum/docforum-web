# ADR 0001 — Routing strategy: HashRouter vs BrowserRouter

**Status:** Decided  
**Date:** 2026-10-20  
**Issue:** [#119](https://github.com/DocForum/docforum-web/issues/119)

---

## Context

The app was originally deployed to GitHub Pages, which cannot rewrite
client-side routes.  A direct request to `https://docforum.github.io/docforum-web/login`
returns a 404 because Pages serves only files that exist on disk.

To work around this, `main.tsx` uses React Router's `HashRouter`:
every route lives after `#` in the URL (`/#/login`, `/#/admin/flags`).

Hash routing has several compounding costs:
- **Ugly URLs** that confuse users and cannot be deep-linked by email
  (`#` is stripped by many email clients).
- **Analytics friction** — analytics tools treat the full URL as the page;
  hash fragments make it impossible to aggregate `/patient/settings` across
  sessions without extra URL-scrubbing work.
- **Emailed links** for password reset, email verification, and
  dependent handover invitations all land as hash URLs (`/#/reset?token=…`).
  Many email clients and SMS gateways either strip or encode the `#` part.
- **Complexity for docforum-core** — if this app is ever served by the API
  server itself (e.g. `GET /` returns `index.html`), the server must not
  try to match hash fragments as routes.

---

## Options considered

### Option A — Keep HashRouter everywhere

**Pros:** Zero deployment risk; works unconditionally on GitHub Pages.  
**Cons:** All the costs listed above persist indefinitely.

### Option B — Migrate to BrowserRouter; require server rewrites

Full migration to `BrowserRouter` requires the host to return `index.html`
for every unknown path (`/*`).

- **GitHub Pages** — cannot be configured to do this.  The standard trick
  (copy `index.html` to `404.html`) redirects all 404s back to the SPA but
  causes a flash and breaks `<link rel="canonical">`.
- **Cloudflare Pages / Netlify** — both natively support `_redirects`
  (Netlify) or a `_headers`/`_routes.json` (Cloudflare Pages) file that
  rewrite `/*` to `/index.html`. Free tier, no build changes required.
- **Served by docforum-core** — the Express / Fastify backend can serve
  `dist/index.html` for `GET *` routes the API doesn't handle, with no
  external CDN needed at all.

**Pros:** Clean URLs, deep-linkable emails, no analytics friction.  
**Cons:** Breaks on GitHub Pages without the `404.html` workaround.

### Option C — Configurable router (this ADR's decision)

Use `BrowserRouter` by default.  Retain `HashRouter` behind a build-time
flag (`VITE_USE_HASH_ROUTER=true`) so GitHub Pages builds continue to work
without any host-side changes.

Add a `HashRedirectShim` component (only mounted in BrowserRouter mode) that
detects a root-path load whose `window.location.hash` starts with `#/` and
replaces the history entry with the clean path.  This keeps old bookmarks and
previously-sent email links working transparently.

**Pros:** Clean URLs everywhere they are supported; backwards-compatible for
GitHub Pages; old hash links keep working; one codebase for all deployment
targets.  
**Cons:** Two code paths to maintain; the `404.html` trick is still needed if
GitHub Pages is ever switched off hash routing.

---

## Decision

**Option C — configurable router.**

- `main.tsx` selects `BrowserRouter` when `VITE_USE_HASH_ROUTER` is absent
  or `false`, and `HashRouter` when it is `true`.
- `.github/workflows/deploy-pages.yml` sets `VITE_USE_HASH_ROUTER: "true"` in
  the build step so the Pages deployment is unaffected.
- `HashRedirectShim` is mounted inside `App` only in BrowserRouter mode.
- Analytics URL scrubbing (`src/utils/analytics.ts`) strips hash-style routes
  (`#/path`) so pageviews are clean regardless of which router is active.

---

## Consequences

- New deployments (Cloudflare Pages, Netlify, or behind docforum-core) get
  clean URLs with no extra configuration beyond omitting
  `VITE_USE_HASH_ROUTER`.
- The GitHub Pages preview continues working unchanged.
- Email links generated by docforum-core should use clean paths; existing
  hash-format links in already-sent emails will redirect transparently.
- If docforum-core ever updates its email link format (reset, verification,
  handover), that PR should coordinate with this repo to confirm the clean
  path lands correctly on both routing modes.
- `ARCHITECTURE_ESSENTIALS.md` "Deployment" section updated to reflect the
  configurable router.
